# Wally

Wally is a food-only AI agent you text (iMessage/SMS) with a companion web app. It orders food and books restaurant reservations. The mascot is Wally the Waiter, a chubby mint-green monster in a waiter's outfit.

Read `docs/product-brief.md` before any product or architecture work. It condenses the PRD into the rules the code must enforce. The canonical character art is `assets/character/wally-canonical.png`.

## Layout

- `apps/web` — Next.js (App Router, TypeScript, Tailwind v4). Onboarding, Home, Taste, Wallet & Limits, Ledger. See `apps/web/AGENTS.md`: this Next.js version has breaking changes, read the bundled docs before writing Next code.
- `packages/core` — `@wally/core`. Framework-free domain code: the connector interface (`connector.ts`) and the policy/approval engine (`policy.ts`).
- `docs/` — product brief and decisions.
- `supabase/migrations` — the database schema, as SQL. `supabase/migrations.test.ts` runs it in an in-process Postgres (PGlite).

Planned, not yet built: memory service, payments service, human ops console. The channel gateway exists in its first form: see "Texting Wally". The conversation orchestrator exists in its first form: see "Ask Wally and the agent".

## Commands

Run from the repo root (npm workspaces, Node 22):

- `npm install`
- `npm run dev` — web app at localhost:3000
- `npm test` — vitest (config in `vitest.config.mts`)
- `npm run typecheck`
- `npm run lint`
- `npm run build`

Run test, typecheck and lint before committing.

## Deploy and CI

- Hosting is Vercel. The Vercel project's Root Directory is `apps/web`; config is in `apps/web/vercel.json`. Pushes to `main` deploy to production, other branches get preview deployments.
- GitHub Actions (`.github/workflows/ci.yml`) runs test, typecheck, lint and build on every push to `main` and every pull request.
- Environment variables are set in the Vercel project settings, mirrored in `.env.example`.

## Rules that are not negotiable

These come from the PRD and exist because of real failures at competitors.

1. **Policy is code, not a prompt.** Every write action (charge, order, booking, cancel) goes through `packages/core/src/policy.ts`. The model never decides whether it may spend. Changes to policy need tests.
2. **Ask every time.** Explicit approval of an itemized ticket before any charge or booking. Only the payer approves.
3. **Submit once.** On timeout or unknown outcome, never retry automatically: check status and escalate to a human.
4. **Fail closed** when payments or checkout are degraded.
5. **Limits can't be changed from chat.** Caps and auto-approve are set on the web only.
6. **Cards never touch chat or the model.** Hosted card capture, tokens only.
7. **Connectors only.** All ordering and booking sources sit behind the `OrderingConnector` interface. No provider-specific code outside a connector.
8. **No unauthorized automation.** No scripted access or polling of OpenTable, Resy, DoorDash or any platform without written authorization. Reservations are booked in the diner's real name, one per meal period, never resold or transferred.
9. **Allergy and dietary data** live in a separately consented, separately deletable store.
10. **Wally always identifies as an AI** and never starts a 1:1 thread with a non-member.

## Web design

- Tokens live in `apps/web/src/app/globals.css`: cool paper background, vest-navy ink, green accents, all drawn from the character art. One typeface, Google Sans (open-licensed, OFL), self-hosted via `@fontsource-variable/google-sans`.
- Positioning runs through all copy: Wally gives the diner every option in one place (delivery apps and restaurants' own sites) and puts local restaurants and their own sites first. Show it, don't argue it: no naming or knocking a delivery app, no talk of fees. See "Positioning" in `docs/product-brief.md`.
- Wally speaks in the first person on the landing page, in onboarding and in Ask Wally ("Hi, I'm Wally, your personal waiter. What can I serve up for you today?").
- The site icon, Apple touch icon and share image are Wally's face, cropped from the canonical art into `src/app/icon.png`, `apple-icon.png` and `opengraph-image.png` (Next.js picks them up by name).
- Wally renders through `src/components/Wally.tsx`. The page background must stay `--paper`, which matches the image backdrop.
- Where there is only room for his face (the strip above the conversation on a phone), use `src/components/WallyFace.tsx`: a drawn face with a `look` prop (smile, glances, wink, delight, thinking, talking, sorry). `AskWally` picks the look from what he is doing and rotates idle looks, so he never holds one expression.
- Gradients are classes in `globals.css` (`fill-green`, `fill-ink`, `tile`, `card`, `composer`, `dock`, `aura`), kept subtle. White text on `fill-green` must stay above 4.5:1.
- A place answer must fit four cards on a phone screen at once, between the sticky strip and the message box. Keep place cards compact (about 113px each) and one per row.
- Onboarding is `/join` (`src/components/JoinFlow.tsx`): name, mobile and ZIP, text consent, then a 6-digit code. Wally speaks each step in a speech bubble and the form is a plain white card.
- Verification: `/api/verify/start` and `/api/verify/check` call Twilio Verify (`src/lib/server/verify.ts`). On success a signed, httpOnly session cookie is set (`src/lib/server/session.ts`) and `/account` reads it.
- Needs `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN`, `TWILIO_VERIFY_SERVICE_SID` and `SESSION_SECRET`. Without them the API answers 503 and the UI says verification isn't switched on. `WALLY_DEV_VERIFY_CODE` is a local-only stand-in, ignored in Vercel production.
- Sign-in at `/signin`: Google OAuth (`/api/auth/google/*`) and emailed sign-in links through Resend (`/api/auth/email/*`). Tokens are typed (`session`, `email-link`) so one can't be used as another. Email links work once. A link asked for from the account page (`link: true`) attaches the email to the signed-in account only when opened in the browser that asked for it (the callback checks the session cookie's id against the token's); anywhere else it is a plain sign-in and `/account?problem=link_elsewhere` says so. Without that check, anyone signed in could mail a sign-in link to someone else's address and fold that person's account into their own when they opened it. The email for a linking request says what it will do.
- `/api/verify/start` and `/api/auth/email/start` cost money per call (a Twilio text, a Resend email) before anyone is signed in, so `src/lib/server/rate-limit.ts` caps them per target and per IP (`wally_rate_hit`, a fixed window in `public.rate_limits`, keys hashed). It fails open with a log line if the database isn't configured or the function is missing, so apply `20261025000000_rate_limits.sql`.
- `/account` is the settings-style profile: contact, name, sign-in methods, delivery apps, reservations, data privacy. Food services come from `src/lib/connectors.ts` and all show "Coming soon"; none may get a working Connect button until a sanctioned integration exists (rule 8). Services show their own mark from `src/lib/brand-logos.ts` (the owner asked for real logos over letter tiles); one we don't hold a mark for shows the icon its own website publishes, fetched in the visitor's browser by `src/components/SiteIcon.tsx` from an icon service, with a letter tile if that fails. Marks only name the service: no copy may suggest a partnership.
- Needs `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `RESEND_API_KEY`, `EMAIL_FROM`. `WALLY_DEV_EMAIL_LINKS=1` shows the link on screen locally.
- Motion classes are in `globals.css`. Anything that transforms Wally must also be listed in the `mix-blend-mode: darken` rule, or a box appears around him.
- Tailwind runs through PostCSS (`postcss.config.mjs`), and the Turbopack build cache is off, after a cached Vercel build shipped stale styles.

## Accounts and the database

- Accounts live in Supabase, used as plain Postgres. Wally keeps its own sign-in; Supabase Auth is not used. Needs `SUPABASE_URL` and `SUPABASE_SECRET_KEY` (`SUPABASE_SERVICE_ROLE_KEY` also works).
- The server reaches the database only through the SQL functions in `supabase/migrations` (`wally_sign_in`, `wally_account`, `wally_set_name`, `wally_set_address`, `wally_delete_account`, `wally_use_link`, and the `wally_chat_*`, `wally_text_*` and `wally_messages` functions), called over the project's REST endpoint by `src/lib/server/db.ts`. `src/lib/server/accounts.ts` and `src/lib/server/conversation.ts` are the only callers. The secret key must never reach the browser.
- Tables have row level security on with no policies, and the functions are granted to `service_role` only, so the publishable key can do nothing. Keep that for every new table and function, and add a test for it.
- Schema changes are new files in `supabase/migrations`, applied by hand in the Supabase SQL editor. Never edit a migration that has been applied.
- The session cookie holds only the account id. A sign-in is plain by default: it returns the account that owns the email or phone and ignores whoever was signed in before. Only the account page's Add/Change/Connect links (`?link=1`) attach an email, phone or Google to the signed-in account, and that can fold another account into it. When tables start referencing accounts, `wally_sign_in` has to move those rows in the fold.
- Without the two variables the app falls back to keeping the profile in the cookie (one browser). A cookie from that mode is turned into an account by `/api/session/upgrade`.
- If the database doesn't answer, sign-in and saves fail with a plain message and change nothing.

## Ask Wally and the agent

- `/ask` is the signed-in chat (`src/components/AskWally.tsx`). Signed-in pages share `SignedInHeader`, with the Ask Wally and Account tabs.
- The agent is Claude, called from `src/lib/server/agent.ts`. `reply(thread, guest, channel, onText)` knows nothing about HTTP or the page: the texting agent must call the same function so both channels get the same Wally. The system prompt lives there and encodes the rules above. Wally has no connectors yet, so the prompt forbids claiming to order or book; relax that only as real connectors arrive. The prompt also holds his voice to short messages (under 45 words unless asked for a recipe or plan).
- Needs `ANTHROPIC_API_KEY`. `WALLY_MODEL` picks the model (default `claude-sonnet-5-5`). Check `node_modules/@anthropic-ai/sdk` types and https://platform.claude.com/docs before changing API parameters. The house rules carry a cache breakpoint, and `withHistoryCache` puts one on the newest message of every request, so the thread so far is read from the prompt cache across the rounds of a turn and across turns; a request may hold at most four breakpoints, so don't add more casually. A `max_tokens` stop on a tool call is never executed (its input is cut off): Claude is told to call again, briefly.
- There is one conversation per account, in `public.messages`, whatever the channel (`web` or `text`). That shared thread is what keeps the website and texting in step. The page re-reads it whenever the tab regains focus.
- `/api/chat`: GET the thread, POST a message (the answer streams back as one JSON event per line), DELETE to erase it. A turn is `wally_chat_begin` (stores the message, enforces `WALLY_DAILY_MESSAGES`, returns recent history), then Claude, then `wally_chat_reply`. If Claude fails, the message is taken back out with `wally_chat_undo` and the page hands the words back to resend.
- Options are structured, not prose: Claude calls the `show_choices` tool, the choices are stored as JSON beside the message, shown as cards on the web, and flattened to a numbered list (`asPlainText`) for text threads and for Claude's own history.
- Finding places: with `GOOGLE_MAPS_API_KEY` set, Claude calls `find_places` (run by `src/lib/server/places.ts` against Google's Places API, near the saved address or a named area) and then `show_places` with the ids it picked. `placeChoices` builds the cards from the search itself: name, miles, open now, rating, website and Maps link. Claude supplies only an emoji and one line of why, so it can't invent a place or a link. Cards are sorted open first, then nearest. Above the cards Wally writes one or two sentences recommending his top pick, in the required `intro` field of `show_places` (`placesIntro` falls back to a plain line from the first card, so cards never arrive without one), from the search's facts only (distance, open and closing time, rating, price); he has no menu data and must never say a dish is available. The search also asks Google for each place's `editorialSummary`, passed to Claude as `known_for`; it is the only thing he may say about what a place serves. That field puts searches in Google's higher (Atmosphere) billing tier.
- "See 4 more" under the latest place cards sends "Show me 4 more" as an ordinary message. `shownPlaces` reads the thread for places already on cards, `describePlaces` marks them `already_shown`, and the prompt tells Claude to show the next four that aren't. A search returns up to 20 places.
- The saved address is set in the bar pinned to the top of `/ask` (`LocationBar`, rendered by `AskWally`, saved through `/api/account/address`). `SignedInHeader` is pinned to the top (3rem tall on phones, 3.75rem from `sm` up), the bar pins under it, and `AskWally`'s strip pins under both: their `top` offsets assume those heights and a 3.5rem bar. The page re-reads the address, and whether Places is on, from `GET /api/chat` on arrival and on focus, so a page left open across a deploy still shows the bar. It is looked up through Places and stored on the account with its coordinates. While typing, the bar shows address suggestions from `GET /api/account/address/suggest` (`suggestAddresses`, Google's Places Autocomplete, US street addresses, billed per lookup, nothing stored); tapping one saves it. Change opens an empty box, and the box's text must stay 16px or iOS zooms the page. The bar's dropdown also offers "Near my location": the browser's location is saved in place of an address, labelled `CURRENT_LOCATION` (`src/lib/chat.ts`), and looked up again on each arrival if the browser still allows it. A search with a saved address is held to a box about 25 miles each way around it (`locationRestriction`, not a bias: with a bias Google answered a Fresno address with Los Angeles places). The address itself is never sent to Claude, only its city and state (`cityOf`), so he knows where "near me" is and that earlier places in the thread may be from elsewhere; the coordinates go only to Google. When the person names somewhere to look around ("burgers near the Pantages theater in Hollywood"), Claude passes it as `area`; `findPlaces` first places it with `findAnchor` (one Places lookup at the cheapest tier: name, location, types), holds the search to a box around it (`AROUND_SPOT_MILES`, 4, or `AROUND_CITY_MILES`, 10, when Google's types say it is a city, town, ZIP or region) and measures every distance from it instead of the saved address. The anchor's name rides on each card as `PlaceInfo.from` ("0.3 mi from Pantages Theatre", web and text alike), `describePlaces` passes `miles_from` and `walkable` (within `WALK_MILES`, 0.8 straight-line), and the prompt tells Claude to orient the whole answer around that spot: which picks are a walk and which a drive, then what each is known for, never mentioning the saved address. If Google can't place the name, the old path stands: the words go in the query and no distance is shown.
- Every place search also asks Google for travel times (`routingSummaries`, with `routingParameters.origin` at the anchor or the saved address and `travelMode` WALK around a named spot, DRIVE otherwise) and for the listing's `takeout`, `delivery`, `dineIn`, `reservable` and `timeZone`. All of these sit inside the Enterprise + Atmosphere tier the search already pays for, so they cost nothing extra; check the first invoice after a mask change all the same, and keep every new field inside that tier (the field table at https://developers.google.com/maps/documentation/places/web-service/data-fields says which). `Place.travel` (mode, minutes, road miles) rides on the card as `PlaceInfo.travel` and is what cards and texts show, time and distance together ("6 min walk · 0.4 mi from Pantages Theatre" on a card, "12 min drive (2.1 mi)" in a text; `howFar` / `howFarParts` in `src/lib/chat.ts`), with straight-line miles kept for the title and for sorting when Google gave no route. `describePlaces` passes `travel`, `walkable` (a walk under `WALK_MINUTES`, 15), `takeout`/`delivery`/`dine_in`/`reservable`, and uses the place's own time zone for `closes` when the person's isn't known (a texter). The prompt has Claude speak in travel times, never straight-line miles, and never offer pickup or delivery from a place whose listing says it doesn't do it.
- Hours: the prompt has Claude pick from places that are open now and say so in the intro (with the top pick's closing time), showing closed ones only when nothing that fits is open or when asked. What a place answer left out rides on the message as a `Choice` with `aside` set (`Aside` in `src/lib/chat.ts`; never a card, `visibleChoices` leaves it out): `closed` counts the search's closed places that didn't make a card and weren't shown before. The page then offers a "🌙 N closed right now" chip beside the others (it sends `CLOSED_ASK`), and a text ends its options with `closedLine(n)` above the other offers.
- Fast food and drive-thrus: under any answer whose place cards aren't all chains, the page offers a "Fast food & drive-thru" chip beside "See 4 more" (`offersFastFood`, `fastFoodAsk` in `src/lib/chat.ts`: it sends "Show me fast food and drive-thru options near <the cards' spot, or me>"), and a text ends its options with `FAST_FOOD_LINE` above the site link. Claude then calls `find_places` with `fast_food: true`, which steers the query toward quick-service places ("… fast food drive-thru"; Google has no type or field for drive-thrus). `src/lib/chains.ts` names the big chains by a listing's name (`chainOf`: site domain, what it's for, and how often that chain has a drive-thru: usually / sometimes / rarely); `describePlaces` passes `chain` and `drive_thru_likely`, the card carries `PlaceInfo.chain` and shows the chain's own icon (`SiteIcon` by its domain, size `sm`) in place of the emoji tile, and the prompt has Claude favor usually-drive-thru chains when a drive-thru was asked for, while saying to confirm, since nothing says whether this location has one. Chain marks only name the chain; never any copy suggesting a partnership.
- A place card's first link is the restaurant's own site, a "Website" pill that glows (`chip-lead`) when it is really the restaurant's own; on an orderable card the glowing pill is "Order with Wally" instead (it sends "Order from <name>" to start the ordering flow) and Website sits plain after it. `isOwnSite` (`src/lib/chat.ts`) decides: a listing's website that is really a marketplace, booking or social page is labelled plain "Website". `describePlaces` passes `own_site` to Claude, and the prompt tells him to favor independent places that have one when the fit is otherwise equal.
- Delivery links on a place card (`deliveryLinks`) open a search for the restaurant's name in DoorDash and Uber Eats. They are not the restaurant's page there: neither app offers a sanctioned lookup, and rule 8 rules out scraping one. The one exception is a listing whose Google website is itself its `/store/` page on the app; that page is used for that chip.
- Google's terms for Places data: show the "Google Maps" attribution with the cards (Google asks for its logo where it fits; the page uses the permitted text form, so swap in the official logo asset if one is supplied), and don't cache Places content other than place IDs. Stored messages hold a snapshot of each card. The open/closed badge is shown only for `OPEN_BADGE_MINUTES` after the answer. Before storing more Places data, or keeping it longer, re-read https://developers.google.com/maps/documentation/places/web-service/policies.
- Without `GOOGLE_MAPS_API_KEY`, Wally falls back to Claude's built-in `web_search` tool to find places (up to three searches a message, each billed by Anthropic), and must ask for the person's area first. With Places on, the web search tool is not offered at all, so review and listing sites never appear beside place cards. A link on a web option card is kept only if it is https and on a site the search returned (`readChoices`). Pages he cites are shown under the answer, which Anthropic's terms require when showing search-backed output to people.
- Messages are plain text, no markdown, so the same words work in a text message. Sources ride inside the text as a closing "Sources:" block (`withSources` / `splitSources` in `src/lib/chat.ts`); the page lifts them out and shows them as links.
- Open item: rule 9. People may mention allergies in conversation, and those messages are stored with the rest of the thread. A separately consented store is still to build before Wally remembers dietary needs.

## Ordering (first connector: MealMe, Square restaurants)

- The agent orders through `src/lib/server/ordering.ts` only: `orderingConnector(accountId)` returns the one `OrderingConnector` (from `packages/core`; MealMe today), `mayHandOff(quote)` is the policy gate every ticket passes (`canHandOff` in `packages/core/src/policy.ts`: the kill switch `WALLY_ORDERING_PAUSED=1`, the quote's age), and `nameMatches` / `sameStore` / `zipOf` tie a venue to a place found elsewhere. The agent never imports a provider's file (rule 7); the model never sees the gate (rule 1). A hand-off connector builds the cart and returns `Quote.handoffUrl`, the venue's own checkout, where the diner sees the ticket again and approves by paying (rule 2); `canSubmit` stays for a connector that places orders itself and needs an approval first.
- `src/lib/server/mealme.ts` talks to MealMe's self-serve API (`https://mealmeai.vercel.app`, `Authorization: Bearer`, key in `MEALME_API_KEY`) and wraps it as `mealmeConnector(customer)`. It covers restaurants that take orders through Square (Cash App ordering) only. Every successful call is billed to Wally (about ten cents); a failed one isn't. A `MenuEntry.itemId` from it packs MealMe's item id with the two Square tokens checkout needs, so a menu read in one turn can be ordered in a later one; it is opaque outside that file. Money fails closed: an item whose price (or an option's) can't be read is left out of the menu, and a checkout whose subtotal or total is missing or doesn't cover subtotal plus tax throws, so a ticket never shows a guessed figure. Dine-in-only items (no PICKUP fulfillment) are never listed.
- The flow in `agent.ts`: `find_menu` (restaurant name + dish) finds the store near the person's ZIP (from the same `orderableStores()` list a place search fetched this turn, so it isn't billed twice) (`orderingZip`: `zipOf` the saved address, else the ZIP under a shared current location by Google's Geocoding API (`zipAt`), else the account ZIP, else one Claude was told in the conversation, else Claude asks) with `storeMatches`, searches its menu, and hands Claude the items and required choices with short ids (`describeMenu`). `order_ticket` (item id, option ids, quantity, a line) checks every required choice is satisfied, builds the cart (`checkout`), and returns one `Choice` carrying a `ticket` (`TicketInfo` in `src/lib/chat.ts`): the restaurant's own subtotal, tax, total and its checkout page.
- The person pays on the restaurant's Square checkout, never through Wally (rules 2 and 6). A ticket is a cart ready to pay, not a placed order; nothing is charged until they pay there. The tools are only offered when `MEALME_API_KEY` is set and the guest has an account id (the MealMe customer id).
- One dish per checkout (with options and quantity): MealMe's Square checkout takes a single item spec and ignores extra cart items. Build a second ticket for a second dish.
- A menu outlives the turn it was read in. When a turn ends with a menu read or ordered from but no ticket built (Claude asked for a required choice), the menu rides on the assistant message as a `Choice` with `menu` set (`MenuSnapshot` in `src/lib/chat.ts`: venue, items and options by the same short ids). It is never a card (`visibleChoices` leaves it out on the web and in texts), but `asPlainText` writes it into Claude's own earlier turn with the ids (`menuLines`), and `savedMenu` restores it at the start of the next turn, so the person's answer goes straight to `order_ticket` with no second read. It is carried for `MENU_TURNS` (3) answers without use, then dropped; a ticket ends it.
- The web shows a ticket as a restaurant check (`Ticket` in `AskWally.tsx`) with a Pay button; `asTexts` writes it as a text card with the pay link; `asPlainText` is what Claude reads back.
- MealMe's catalog descriptions are the restaurant's; Wally may quote prices and choices from `find_menu` only.
- A place search near the saved address also fetches the orderable stores for that ZIP once per turn (`orderableStores`) and marks each Google place that is one of them (`sameStore`: names match loosely both ways and street numbers agree) with `orders: true` on its `PlaceInfo`. The card shows an "Order with Wally" badge, texts say the same, `describePlaces` passes `can_order`, and the prompt says a can_order place that fits the ask always gets a card (preferred for the top spot only when it fits as well, is as close and as open). The store list has no cuisine filter, so `STORES_PER_TURN` (80, within 8 miles) is asked for so a cuisine search can find its matches in it; MealMe answers 500 to a search that wide, so `searchStores` steps down (40 within 6, then 20) before giving up; a place search also adds up to `MAX_NAMED_ORDERABLE` orderable stores whose name carries a word of the query (`storeNamedFor`, filler words ignored) that Google's twenty left out, looked up through `orderablePlaces`; for "mexican spots you can order from" Claude runs find_places and shows the can_order matches first, then the best others, with an intro that says which are ordered right here and which through the chips on their card. When the person asks what Wally can order from, `find_orderable_places` takes the nearest open stores (`MAX_ORDERABLE`, 8), looks each up in Google Places by name and address (`orderablePlaces`, one Places search per store, matched with `sameStore`; one not found gets a plain card with a Maps search link) and hands them to Claude like any search result, so `show_places` draws the usual cards with the badge. The mark is a navy scalloped check seal right after the name (`OrderCheck`, `--ink`, so it reads as a credential rather than another green chip) plus the leading "Order with Wally" chip; never a different card layout.

## Texting Wally

- `src/lib/server/texting.ts` is the channel gateway. A text arrives at `/api/text/sendblue` (iMessage, through Sendblue) or `/api/text/twilio` (plain SMS); the route checks it really came from the provider, answers the provider at once, and does the work in `after()`. `handleInbound` then runs the same turn as the website: `wally_text_begin`, `reply(..., "text")`, `wally_chat_reply`, and sends the answer back through the provider the text came in by, as `asTexts` (`src/lib/chat.ts`) lays it out: his words in one bubble, then the options in a second, each a small card (numbered name with its emoji, a facts line, a few words on what it is, a short link). A text card links the place's website; without one it offers DoorDash and Uber Eats as short links (`textDeliveryLinks`, served by `/go/[app]/[slug]`, which redirects to that app's search for the name); every place card then ends with its Google Maps link (`Map: …`), asked for by the owner on 2026-10-25 (an earlier rule kept Maps links out of texts). Every set of options ends with "Visit Wally for more options" and a link to `/ask`, which opens the same thread at its latest message. `asPlainText` is still what Claude reads back as history.
- A text is matched to an account by the verified phone number on it (`wally_text_begin`). A number with no account gets one fixed line pointing at the account page, and nothing is stored. The account page's "Connect by text" opens a ready-written text holding a `connectCode` (account id plus a daily signature); when it arrives, `readConnectCode` and `linkPhone` put the sending number on that account, so a phone can be connected without Twilio Verify. Wally never texts first (rule 10): every outbound text is a reply.
- The first text in a thread gets a fixed hello that says he is an AI, then his contact card (`/wally.vcf`, built in `src/app/wally.vcf/route.ts` with his photo from `src/lib/wally-photo.ts`). That text and web are one conversation is said on his first answer and again only after a week without texts from him (`webNudgeDue`): as a line under the options link, or as a P.S. (`NOTICE.web`) when the answer has no options.
- STOP, START and HELP are handled before anything else (`keywordOf`), only when they are the whole message. `accounts.text_stopped` silences him until START. Twilio answers those words itself, so Wally doesn't answer them again there.
- Deliveries carry the provider's message id (`messages.external_id`, unique), so a retried webhook is dropped as a duplicate.
- Twilio webhooks are checked by signature (`twilioSignatureValid`; needs `APP_URL` to be the public origin). Sendblue webhooks are checked by a secret we choose, carried in the webhook address (`?key=`).
- The website polls `GET /api/chat` every six seconds while visible, so texts show up there without a refresh. Web messages are not pushed to the phone; the phone sees them as context the next time the person texts.
- Not built yet: the three-second debounce for several texts in a row, photos, group threads, per-line send limits, and a time zone for texters (so closing times aren't quoted by text).
- Needs `SENDBLUE_API_KEY_ID`, `SENDBLUE_API_SECRET_KEY`, `SENDBLUE_FROM_NUMBER`, `SENDBLUE_WEBHOOK_SECRET` and/or `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN`, `TWILIO_MESSAGING_SERVICE_SID` or `TWILIO_FROM_NUMBER`; plus `NEXT_PUBLIC_WALLY_NUMBER` for the links and the card.

## When a page breaks

- `src/app/error.tsx` and `src/app/global-error.tsx` both render `components/Recover.tsx`. The usual cause is a deploy landing while a page is open: the old page asks for script files the new version no longer has, and the load fails. `Recover` reloads the page once (at most once a minute, tracked in session storage), and only shows its message if that didn't help.
- It also posts the error to `/api/client-error`, which writes it to the server log as `[client]`. Look there first when someone reports a broken page.
- `Recover` uses inline styles because the app-wide error page renders without the site's stylesheet.

## Conventions

- TypeScript strict. Money is integer cents.
- Tickets, confirmations and errors use neutral, exact language. Personality lives elsewhere, and never while money or a problem is on the table.
- Don't use `next/font/google`; the build environment can't reach Google Fonts. Use system fonts or `next/font/local`.
- Vercel installs only the web app's dependencies, not the root's. Anything `apps/web` imports at build time must be in `apps/web/package.json`. Test files are excluded from the web type check for this reason.
- Never commit secrets. Add new env vars to `.env.example`.
